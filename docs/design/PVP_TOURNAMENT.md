# 定期PvP大会 — 要件・基本設計・詳細設計

Revision 0.2 / 2026-09-13

確定: PvEを基本とし、定期大会としてPvPを実装する。戦闘はオート、50職と職業固定スキルを維持する。
提案: 以下の頻度、編成、試合形式、補正、報酬はD09の初期案。大会の存在への承認を細部全件の承認に広げない。

## 1. プレイヤー体験と初期ルール

週1回の4人対4人の大会。受付期間にチーム・職業・配分・装備・作戦を登録し、締切後に保存したビルドでオート戦闘を行う。試合時刻に4人全員がPC前にいることを必須にしない。プレイヤー自身のキャラクターを複数作る方式ではなく、登録した情報を対戦専用に保存して比較する方式とする。

受付48時間、開始日時は開催設定のUTC値を正本としてユーザーのローカル時刻で表示。特定曜日・時刻・実際の初回開催日は未定。公開告知前に確定する。

初期枠は1大会64チーム、1アカウント1チーム。同ワールド、異なる4アカウントで編成。PvPはNPC補完しない。0〜1チームなら開催中止、2チーム以上なら単一敗退トーナメント。枠は測定後に拡張可能。エントリー料は無料。

3ゲームの合計得点で各対戦の勝者を決定。常に3ゲーム行い、1ゲーム180秒上限。勝ち2点/引分け1点/負け0点。先に2勝した場合も第3ゲームの計算を省略しない。各ゲームでHP/MP/CD/蘇生回数/装備の致死耐えをリセットする。

## 2. 大会用ビルド

使用職業はそのキャラクターが解放済みの職だけ。大会内ではキャラLv100・職Lv50として評価し、ステータス505点、スキル53点までの専用配分を登録できる。通常育成のLv・経験値・習得状態へ書き戻さない。

装備は本人所有の5部位を持ち込む。職別武器制限、3/6/10点の装備スキル、最大4系統、合成後の本人専用状態をそのまま検証する。レアリティ・装備性能・技能点は保持するため装備差は残る。レベル統一を「全員完全同条件」と説明しない。固定装備制の別大会は将来案であって初期必須ではない。

snapshotにはaccount_id、character_id、job_id、tournament_allocations、item_idsと全性能/Version、gear_skills、AI、content_version、pvp_profile_version、署名またはサーバー保存hashを含む。クライアントが提示する能力値ではなく公式保存状態から組み立てる。

各人が自分の登録版に同意し、リーダー変更や1人分の差替えでもteam_revisionを増やして全員の同意を解除する。締切時点で完全な4人と4同意を持つチームだけ採用する。締切後は変更不可。

装備の多重貸出登録対策として、同一tournament_id内でitem_idが複数参加者のsnapshotに含まれることを禁止する。エントリーと編集時に原子的に予約し、締切前の辞退で解放、締切後は大会終了まで履歴予約を残す。予約は大会登録への重複防止であり、既存のbindingや実物の取引権を変更しない。登録後に実物を売却しても既存snapshotは不変、新所有者はその大会に同じitem_idを登録できない。

登録・観戦はPvE出撃中も可能な提案。大会内の対戦は記録ビルドの比較であり、通常のexpedition_members.activeを増やさない。1活動キャラ・通常同時出撃1件を維持する。PvEの全滅制限中でも登録でき、大会敗北でPvEのcooldownを変更しない。

## 3. 戦闘とバランスの分離

Combat.Advanceの同じコアにmode=PVPとpvp_profile_versionを渡す。職業・スキルIDを複製せず、最終効果への補正を別定義で適用する。初期係数は与ダメージ100%、直接/継続回復60%、シールド60%。全てプレイテスト前の値。PvEの係数を変更しない。

敵味方それぞれ前列2/後列2。相手のプレイヤーをenemy teamとして同じ標的規則を評価する。挑発は効果中の敵対単体行動だけを挑発者へ変更し、味方回復や範囲スキルの対象は変えない。指定対象が不適格なら通常の候補選択に戻る。マークは挑発と混同しない。

所持消耗品の使用、アイテムドロップ、通常EXP/JEXP/Gの付与は大会内で行わない。召喚は既存ルールどおり本人1枠、生存人数に数えず、本人KOで停止する。蘇生は1キャラ1ゲーム1回、全員KO後には発動しない。

各ゲームは同時刻の詠唱完了を解決してからKOを反映。両チーム同時全滅は引分け。一方のみ全滅ならそのチームが敗北。

180秒で未決着なら、生存する本人キャラ数が多い側、次にHP率合計が高い側の順で判定する。HP率は各本人のfloor(10000*currentHP/maxHP)の和。KOは0、召喚・シールド・累積回復を含めない。それでも等しければそのゲームは引分け。

3ゲームの得点同点なら、3ゲーム終了時の本人HP率合計の総和を比較。それも同値なら事前規定の大会seedに基づく抽選で勝ち上がりを決め、UIに「同点抽選」と表示する。先着順・接続速度・切断・運営者の任意入力で決めない。

無効な効果再帰、回復だけの無期限試合、最速化の上限突破は既存の上限と180秒制限で防ぐ。初級職のPvE採用理由を守りつつ、PvPでは被ダメージ・回復・勝率・採用率を別に計測する。

## 4. 組合せ・乱数・公開

締切前に公式側で暗号学的乱数からevent_secretを生成しhashを公開する。締切後に確定したチーム集合hashを保存し、seedと集合から決定的にシャッフルする。ブラケットは参加数以上の最小の2のべき乗枠を用い、空き枠は初回不戦勝として扱う。誰に不戦勝が付くかも同じseedに従う。

ゲームごとの乱数はevent_secret、tournament_id、match_id、game_index、用途名から派生させる。組合せ、通常戦闘、同点抽選はストリームを分け、同じ入力で一意の結果になる。処理失敗時に新しいseedを振らない。全試合確定後にseedと使用Versionを公開し再現検証に使えるようにする。

フルビルドと相手AIは全チームの登録締切まで非公開。大会中は公開プロフィールと確定した対戦結果だけ表示し、完全リプレイは大会結果確定後に公開する初期案。全員ロック済みでも、不要な秘密とAPI認証情報はリプレイへ含めない。

## 5. 公式判定と障害

公式計算基盤を持つB案では、登録・組合せ・勝敗・報酬を運営の信頼済みサービスが確定する。プレイヤーP2PホストのWIN申告、全員一致の自己申告、署名のないローカルセーブを公式結果として採用しない。伝送の署名だけで獲得過程が正しかったと判定しない。

`DRAFT → REGISTRATION → LOCKED → RUNNING → FINALIZING → COMPLETED`。開催不足はREGISTRATIONからCANCELLED。予期せぬ障害はRUNNINGからSUSPENDED、復旧後に同じ登録版とseedで再開する。

ワーカーはleaseを短いDB取引で取得し、計算中は行ロックを保持しない。game_idごとの結果一意制約とVersion/CASで二重精算を防ぐ。勝敗・ブラケット進行・outboxを同じ取引で保存する。敗退者の接続切れを敗北理由として扱わず、登録後は切断しても同じビルドで続く。

全試合の整合性検査が終わるまで報酬を発行しない。障害中は「中断/集計中」と表示する。登録以降に利用停止となったアカウントは当該チームを失格扱いとし、理由付き監査記録を残す。再計算が必要なら報酬前に大会を中断する。結果確定後の訂正は別の訂正Versionと補填operationを記録する。

D01が完全P2PのA案に決まった場合、この公式判定層を省略して合格扱いにはしない。公式大会を名乗る範囲と不正対策を再設計する。

## 6. API・データ・画面

既存API.mdの認証・所有権・Idempotency-Key・expected_version・エラー形式を引き継ぐ。

|API|入力/結果|
|---|---|
|GET /v1/tournaments|受付/開催/結果、時刻、ルールVersion、空き枠|
|GET /v1/tournaments/{id}|公開ルール、seed_commit、公開ブラケット、結果|
|POST /v1/tournaments/{id}/entries|team_id、4人のID。各人への同意待ちentry_idを発行|
|PUT /v1/tournaments/{id}/entries/{entry_id}/build|本人のjob/配分/装備ID/AIとteam_revision。公式状態で再構築し同意解除|
|POST /v1/tournaments/{id}/entries/{entry_id}/confirm|本人のsnapshot_hashとteam_revision。締切前のみ|
|POST /v1/tournaments/{id}/entries/{entry_id}/withdraw|辞退。締切前だけ予約解除、締切後は公式に棄権として記録|
|GET /v1/tournaments/{id}/matches/{match_id}/replay|公開時刻/権限を満たすリプレイ。隠しseedや非公開ビルドを先渡ししない|

結果を端末が書くPOST /resultは設けない。WSSはtournament.entry_changed/locked/match_finalized/suspended/completedを追加する。

|追加データ|主要制約|
|---|---|
|tournaments|id、status、registration_times、rules/content_version、seed_commit、secret_ref、version|
|tournament_entries|id、tournament_id、team_id、revision、status。大会内team一意|
|tournament_members|entry_id、account_id、snapshot、snapshot_hash、confirmed_revision。大会内account一意|
|tournament_item_reservations|tournament_id、item_id、entry_id、member_id。予約有効中は大会内item_id一意|
|tournament_matches|id、round、slot、entry_a/b、status、winner、version。大会内round/slot一意|
|tournament_games|match_id、game_index0..2、checkpoint、result_hash、score、hp_sum。組合せ一意|
|tournament_rewards|tournament_id、account_id、reward_code、operation_id。一意な付与receipt|

追加画面は「大会」入口、ルールと受付残時間、4人の同意状態、大会用ビルドとPvEとの差分、対戦表、結果、公開後リプレイ。参加前にレベル補正だけで装備差は残ること、敗北で装備を失わないことを表示する。

## 7. 報酬・検証

報酬は非交換の称号、プロフィール枠、外見色を初期案とする。PvE性能に必須の装備やスキルを大会限定にしない。対戦中ドロップ・参加賞G・賭け金・現金賞金を自動追加しない。ドロップ品の交換可能要件はPvEの品に対して維持する。

QA-P01: 4人全員同意/差替え時失効/1アカウント1チーム/同装備重複/締切境界。
QA-P02: 解放職・53SP・505点・装備武器制限・通常状態非変更・全滅制限非変更。
QA-P03: 0/1/2/3/64チーム、ブラケット不戦勝、3ゲーム、180秒、同時KO、同点抽選の再現。
QA-P04: タイムアウトと再試行、切断、結果改ざん、二重ジョブ、報酬重複、seed/Version一致。
QA-P05: PvE係数不変、回復/盾補正、召喚・蘇生・挑発・DoT、50職の役割別比較。
QA-P06: 観戦の認可、受付中の相手ビルド非公開、取得権限、公開タイミング、UI時刻表示。

この更新は設計であり、QA-P01〜06を実行済みにはしない。実装Task YA-P01/02/03へ分割する。
