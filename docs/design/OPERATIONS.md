# 運用・監視・復旧の設計

YA-D03 / 2026-10-02。旧section-6を[REQUIREMENTS](REQUIREMENTS.md)のNFR02–07/09/12、[COMBAT_CORE_V1](COMBAT_CORE_V1.md)、[DATA_MODEL](DATA_MODEL.md)へ接続する。設計・試験計画であり、運用環境が存在する・目標達成・契約/課金/本番操作が承認されたという記録ではない。

## 1. 環境と負荷

development/staging/productionのデータ・設定を混在させない。比較案Bは1アプリ/1DBから開始し、保存先の障害領域を分ける。採用ホスト、DB、費用、恒久運用はD01と実測後に確定する。

接続数CCUと離席を含む稼働冒険Eを別に数える。1冒険のイベント率r、1イベント計算時間t、保存間隔s、品生成率gを測定し、CPUの概算E×r×t、保存頻度E/s、品増加E×gを同時に記録する。旧50/200/1000接続、100/1000/5000冒険は段階試験候補で、対応人数の保証ではない。クライアント描画/RAMはYA-01の別計測。

## 2. 監視と目標

既存NFRのAPI p95 300ms/経済p95 500ms、月99.5%、RPO5分/RTO60分は設計目標でSLAではない。active_connections、active_expeditions、simulation_lag、計算時間、queue_age/outbox_age、DB待機/deadlock、エラー率、メモリ/GC、容量、所有権/台帳整合を分けて観測する。

旧初期アラート（5xx>1%が5分、lag>30秒が5分、outbox>60秒、DB空き20%未満、24時間backup失敗、台帳不整合1件）は調整候補。通知先/実閾値/自動停止の権限は実運用設計で定義する。設計文書の更新で既存サービスを停止したり警告設定を変えない。

## 3. 記録の境界

request/operation/account/expedition/run/grant/item/content Versionで追跡できる設計を維持する。生Steamチケット、token、秘密鍵はログへ載せない。通常ユーザー/管理者分離、管理操作の理由と前後記録は旧設計候補を現行FR28/NFR09へ接続する。新規認証方式、MFA導入、管理権限変更は今回の実行対象ではない。未検証端末報酬を公式経済へマージしない。

## 4. 復旧と精算

候補手順は新規出撃/経済操作の受付停止 → 保存状態復元 → schema/content互換確認 → 古いlease失効 → 未精算run/outboxの同一操作ID再開 → 台帳/所有者/活動出撃一意の検証 → 運営確認 → 再開。実操作の許可・安全な実行順は対応運用Taskで確定する。

停止時間を全滅へ変換しない。追いつきは元の8時間指示まで。全滅制限は公式全滅イベント+300秒で、復旧処理完了時に追加300秒を付けない。補填は元報酬の再発行でなく別の一意操作として追跡する。復元訓練/障害注入は未実行。

旧日次backup/継続WAL、日次7世代/週次4世代はDBと予算に依存する提案。暗号化・外部保存の本番導入、購入、credentials変更をこの文書で許可しない。

## 5. 更新と保持

指示開始のcontent Versionを8時間と未精算分へ固定し、新しい調整を進行中の戦闘へ途中投入しない。旧定義/互換処理は未精算分の終了まで保持する案。互換列追加→移行→旧列整理は物理設計候補で、migrationを実施しない。main公開は別の明示されたgate。

旧保持期間（chat30日、通報90日、詳細戦闘7日、要約90日、経済365日以上）は初期案。法的必須期間とは説明しない。利用地域/運営方針/削除と一意キー履歴の両立は公開前の判断に残す。
