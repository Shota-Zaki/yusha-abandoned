データモデル・整合性設計

設計補足 v0.1.1 / 2026-09-13。Repositoryの基本設計・API・詳細設計と合わせて使用する。DDLの実行結果ではなく、実装契約である。

1. 型と所有権

PostgreSQLを唯一の永続状態の正本とする。ゲームのアイテム・通貨をSteam Inventoryにも同時に所有させる構成は採用しない。IDはサーバー発行UUID、SteamIDは十進数文字列（UInt64範囲）、金額はbigint、UTC時刻はtimestamptz、楽観ロック用versionはbigint。

帳簿は追記型。経済データを消去・上書きして履歴の参照を壊さない。退会時の表示名の削除と、整合性を保つ取引履歴の保持は別処理とし、保存方針は公開前に確認する。

3. 予約を一元化する理由

出撃、直接交換、出品が別の予約表だけを見ると、同じ品が複数用途に予約されるおそれがある。本案ではitemsのreservation_kind/reservation_idを最終的な共通状態とする。空き→予約の遷移は品の行ロック内で行い、空き以外から別の予約へ直接変えない。

reservation_kindはNONE/EXPEDITION/TRADE/MARKET。誤消費防止のユーザー保護ロックは別のboolean。locationはBAG/WAREHOUSE/EQUIPPED/REWARD_INBOX/TRADE_ESCROW/MARKET_ESCROW/CONSUMED。binding・場所・予約・保護を混同しない。

4. ロック順序

全更新で、account ID昇順 → character ID昇順 → party/expedition → item ID昇順 → wallet/material ID昇順 → trade/listing → reward/ledger/operation、の順で取得する。

事前読取は対象IDの特定に使用できるが、最終取得後にVersionと前提を再確認する。READ COMMITTEDと必要行へのFOR UPDATEを基本とし、一意制約を最終防壁にする。より強い分離が必要な集計だけSERIALIZABLEを検討する。行ロック・待機・デッドロックの挙動はPostgreSQL公式仕様に従う。[S07]

デッドロック/直列化競合は同じ操作IDで最大3回、短いランダム待機を挟み再試行。プレイヤーへの二重課金を避けるため新しいIDに変更しない。

ワーカーのlease取得と戦闘計算を分ける。計算中にDBの行ロックを保持しない。保存時にlease_tokenとversionを再検証し、古いワーカーの結果を拒否する。

5. 合成の確定処理

① 操作IDの既存receiptを確認する。② アカウント・キャラ・装備・アクセサリー・財布・素材を順にロックする。③ 見積期限60秒、所有者、Version、予約なし、保護なし、ソケット適合、残高を再検証する。④ アクセサリーを消費し、ソケットを更新し、装備を永久に本人専用へ変更する。⑤ 費用、履歴、receipt、outboxを同じDB取引に保存する。⑥ コミット後に通知する。

途中の例外は全変更を取り消す。コミット後の通知失敗では取り消さず、同じ操作IDで結果を返す。見積もりは予約ではないので、見積後に売却された品は確定時に拒否する。

6. 直接交換・取引所

交換の提示ゴールドはreservedに積む。確定でbalanceとreservedを同時に減らし、相手口座へ増加する。取消ではreservedだけを解放する。

市場購入は買い手の利用可能額を検証し、代金引落・売り手受取・手数料焼却・所有者移転・受取枠変換・出品SOLD・receipt・outboxを同じ取引で確定する。売り手への入金を後続の別APIへ委ねない。

商品の受取枠は出品時から返却用を予約する。売買成立時に売り手の返却予約を解放し、買い手の受取枠を現品へ変換する。購入直前に買い手の空きをロック内で検証する。

7. コンテンツの入力契約

JobDefはid/tier/requirements/profile/allowed_weapons/identity_effect/active_skill_ids[4]/passive_skill_ids[2]。 SkillDefはid/job_id/kind/program/element/max_rank=20/evolution_ranks=[1,5,10,20]/stage_names[4]/coefficients_bp[4]/mp_costs[4]/cooldown_ms/effect_group/target_rule。 DungeonDefはid/level/unlock_requirements/rooms/difficulty_weights/enemies/reward_rules/time_limits。

AIルールはpriority0〜7、skill_id、condition_code、operator、threshold、target_code、stage_mode、reserve_mp_percent0〜100。任意スクリプトは入力させない。

全参照、一意ID、解放の循環、点数予算、抽選行の合計、由来限定スキル、数値上限を読み込み時に検証し、失敗したコンテンツVersionを有効化しない。

境界条件・レビューでの修正

設計補足 v0.1.1。この資料はRepositoryに保存したv0.1の曖昧さを解消する。現時点ではRepository未反映であり、統合後は各元文書へ反映して重複する正本を残さない。

1. 全滅後300秒の起点

対象位置: REQUIREMENTS FR20、DETAILED_DESIGN 8〜9章。

修正前: 全滅処理時のserver_now+300秒。

修正後: wipe_at = expedition.starts_at + wipe_event.sim_ms、cooldown_until = max(既存値, wipe_at + 300秒)。新規出撃は、アカウントの未精算イベントを現在時刻まで反映してから判定する。

理由: 離席分の追いつき処理で過去の全滅を発見したとき、ログインした瞬間からさらに5分待たせないため。基準は端末時計ではなくサーバーのイベント時刻である。

例: 12:00全滅、12:20に復帰なら制限は12:05に終了済み。12:03に復帰なら残り2分。全滅から299999msは不可、300000msは可。

2. 時間の量子化

対象位置: DETAILED_DESIGNの行動間隔式と100ms時刻契約。

修正前: 速度計算後の任意の整数msと、100ms単位の処理が混在。

修正後: 全ての予定時刻の差分は、能力補正と最短間隔の適用後に100 * ceil(ms / 100)へ切り上げる。800msの最低間隔は維持する。詠唱、CD、効果持続、移動、消耗品CDも同じ処理。

理由: 高速化で過剰な行動回数を与えず、まとめ処理と細分処理の境界を一致させるため。

3. 戦闘と周回の境界

battleは1ルーム、runは通常4ルーム+ボス1ルーム、expeditionは8時間までの反復指示。

HP/MPはルームをまたいで維持。ルーム勝利後、KOの味方は次ルーム開始時にHP20%で復帰し、MPはKO時点の値を保持する。全員KOはこの復帰より先に全滅判定となる。次周回開始時は街帰還扱いで全員HP/MP全回復。

召喚、盾、DoT、HoT、能力強化/弱体はルーム終了時に解除。CDは共通の論理時間上で継続し、移動5秒の経過も含める。スキルMVの蘇生制限は1ルーム1人1回。装備G01の致死耐えは1周回1回で、ルームをまたいでも復活しない。

4. 出撃予約と直前操作

出撃開始では参加アカウントと使用品・消耗品を予約し、全員分を同時に確定する。取引中、他の出撃中、合成対象、受取枠不足のメンバーがいれば誰も出撃しない。

同一アカウントの新しい指示を受理する前に旧指示を終了・精算する。古いワーカーが新しい指示の品やcooldownへ後から書き込まないよう、expedition ID、lease、versionを検証する。

5. 8時間の最終時刻

期限と同時刻までの詠唱完了・ダメージ・KO・ルーム完了を解決し、その後に終了する。期限と同時刻に新しい行動・ルーム・周回を開始しない。同時刻に全滅した場合は、期限終了で隠さず全滅として扱う。

6. 乱数の再現契約

v0.1.1の設計案は、サーバーの暗号学的乱数から32バイトの秘密鍵を生成し、HMAC-SHA256で用途別・連番別の決定的な乱数を得る方式とする。クライアントへ鍵を渡さない。実装時に固定ベクトルと負荷を検証し、方式を変える場合はcombat_versionを上げる。

メッセージはASCIIでv1|stream|expedition-id|run-index|room-index|counter、streamはhit/crit/variance/drop/gear/pityに固定。UUIDは小文字ハイフン付き、整数は符号なし十進表記、余分な空白なし。digestの先頭8バイトをbig-endian unsigned64として読む。

整数範囲[a,b]はn=b-a+1、limit=floor(2^64/n)*nとし、x>=limitならcounterを進めて再試行、採用時はa+(x mod n)。単純な剰余だけで偏りを作らない。乱数counterを各チェックポイントへ保存する。

この方式の具体コードと暗号APIは実装対象であり、この資料で性能・正しい実装を保証したものではない。

運用・監視・検証設計

1. 環境と容量

development/staging/productionでDB・設定・管理権限を分ける。サーバーとDBは1つの管理環境から始め、バックアップ保存先は故障領域を分離する。運営用ホストの契約先・予算はD01の確認事項で、契約済みではない。

50/200/1000接続相当と、100/1000/5000稼働冒険のシナリオを分けて測定する。これは試験計画であり対応人数の保証ではない。費用は実測後にホスト・DB・転送・保存・監視の料金から算定する。

可用性99.5%/月、RPO5分以内、RTO60分以内を設計目標とする。SLAや達成実績ではない。

3. 記録と安全性

ログはrequest_id、operation_id、内部account_id、expedition_id、run_id、grant_id、item_id、content_versionで追跡可能にする。生Steamチケット、token、秘密鍵は記録しない。

通常ユーザーと運営管理者の認証・権限を分離。管理者は多要素認証を用い、補填・回収・利用停止には実行者、理由、対象、前後の記録を残す。ゲーム側では全ての対象IDに所有者・役割・worldの検証を行う。

公式世界の品を端末保存とマージしない。ローカル試験用認証・報酬生成が本番設定で有効にならない検査を設ける。クライアントに報酬決定権を与えない設計を基本とし、外部のチート検知だけで複製防止を代替しない。

4. バックアップ・復旧

日次の基礎バックアップと継続WAL保存を候補とし、暗号化して本体とは別の保存先へ送る。日次7世代/週次4世代を初期案とする。実際の方式は運営予算確定後に選ぶ。

復旧順は、新規出撃・経済操作停止 → DB復元 → schema/content整合 → lease失効 → 未精算run/outboxの冪等再開 → 台帳・所有者・同時出撃一意の検証 → 運営確認 → 再開。

停止時間そのものを全滅に変換しない。復旧後の進行は指示開始から8時間までを上限に追いつく。全滅が過去の時刻に確定した場合の300秒は、再計算完了時ではなくサーバーが再現した全滅時刻から数える。EDGE_CASES.mdの時刻契約を優先する。

補填は別の一意なoperation_idで行い、既に付与した報酬を再発行する方式にしない。復元訓練は実装後に実施する。

5. 更新と保持

開始時のcontent_versionを最大8時間の指示と未精算分に固定する。新しい調整値を既存戦闘へ途中投入しない。旧定義と互換ロジックを未精算分がなくなるまで保持する。

DB変更は互換列追加→移行→旧列整理の順。公開ブランチmainへは配布・実行に必要なファイルだけを選別し、workの設計・Task・証跡を丸ごと公開用構成へ混ぜない。

保持期間の仮案: チャット30日、通報証跡90日、戦闘詳細7日、戦闘要約90日、経済台帳365日以上。冪等判定に必要な薄いID記録は別途保持する。この期間を法的必須期間とは説明しない。利用地域と運営方針は公開前に確認する。
